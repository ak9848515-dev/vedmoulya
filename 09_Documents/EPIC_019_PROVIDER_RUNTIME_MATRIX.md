# EPIC-019 — Provider Runtime Evidence Matrix

> **VedMoulya must never claim a provider, model, API, GitHub repository, or automation capability exists just because it exists in a catalog.**
> Catalog evidence ≠ runtime capability. Configuration ≠ availability. Availability ≠ execution. Execution ≠ successful outcome.
>
> This matrix is derived from the repository source at the time of writing (2026-08-12):
>
> - Catalog: `packages/providers/src/catalog/provider-catalog.ts`
> - Runtime registry (single source of truth): `packages/core/src/startup/provider-runtime.ts`
> - Registration: `services/orchestrator/src/index.ts` (`registerPlatformProviders`)
> - Adapters: `services/orchestrator/src/providers/`
> - Production validation: `services/api/src/infrastructure/ProductionAIConfig.ts` + `packages/core/src/config/index.ts` (`getConfig`)

## Runtime state vocabulary (EPIC-019)

| Status                | Meaning                                                                                                                                                    |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CONFIGURED`          | Adapter exists + key present → will be registered by `registerPlatformProviders`.                                                                          |
| `AVAILABLE`           | Adapter exists, dormant (no key) — documented for completeness; currently not emitted by the registry (key-absent real providers report `NOT_CONFIGURED`). |
| `NOT_CONFIGURED`      | Adapter exists + key absent → not registered.                                                                                                              |
| `UNSUPPORTED_RUNTIME` | Taxonomy/catalog only — **no ProviderAdapter exists** in this repository. A set key is never consumed.                                                     |
| `MOCK`                | Deterministic provider active (dev/test default, or explicit `AI_ENABLE_MOCK=true` production opt-in).                                                     |
| `DISABLED`            | Present but intentionally not registered (mock in production without the explicit opt-in).                                                                 |
| `ERROR`               | Key present but fails the strength heuristic (< 32 chars → production fail-fast would reject).                                                             |

## The four boundaries, enforced

1. **Catalog evidence ≠ runtime capability** — Anthropic, Google, OpenRouter, Ollama exist in `provider-catalog.ts` but have `adapter: null` in the runtime registry. `AI_DEFAULT_PROVIDER=anthropic` fails fast in production/staging (both `getConfig` and `validateProductionAIConfig`); development reports `UNSUPPORTED_RUNTIME` honestly.
2. **Configuration ≠ availability** — a set `AI_ANTHROPIC_API_KEY`/`AI_GOOGLE_API_KEY` is validated as a real secret but **never** counts as an execution path (production AI gate requires OpenAI or DeepSeek, or the explicit mock opt-in).
3. **Availability ≠ execution** — a registered adapter is AVAILABLE; a successful outcome is only claimed when live execution was actually attempted. DeepSeek/OpenAI live calls remain **operator steps** (no fabricated live-provider claims).
4. **Execution ≠ successful outcome** — runtime health/outcomes are reported by the existing `HealthChecker` / provider health probes, never assumed from registration.

## Where the truth lives (single source of truth)

| Layer              | Mechanism                                                                                                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Runtime registry   | `PROVIDER_RUNTIME_DESCRIPTORS` + `readProviderRuntimeState` / `runtimeExecutionReady` / `validateDefaultProvider` in `packages/core/src/startup/provider-runtime.ts` (pure, testable) |
| Configuration      | `getConfig()` (config/index.ts) throws fail-fast when `AI_DEFAULT_PROVIDER` names a catalog-only family in strict modes                                                               |
| Production gateway | `validateProductionAIConfig()` (services/api) uses the same registry states                                                                                                           |
| Registration       | `registerPlatformProviders` (services/orchestrator) — the orchestrator test _"provider runtime registry agrees with registration"_ enforces the contract                              |
| Diagnostics        | Preflight + `npm run doctor` print the registry states; the UI surfaces the same vocabulary                                                                                           |
