## 1. Mission

Connect AI World intelligence (EPIC-012C) with VedMoulya's application/content/factory ecosystem (EPIC-006/007/008/009/010). For any requested outcome, VedMoulya must now answer:

> WHAT CAPABILITIES ARE REQUIRED → WHICH PROVIDERS/MODELS/TOOLS CAN PERFORM THEM → HOW RELIABLY THEY CAN BE AUTOMATED → WHAT THE BEST EXECUTION PLAN IS → WHERE HUMAN APPROVAL IS REQUIRED

The system knows the difference between **"AI can do this"** (capability), **"VedMoulya can automate this"** (integrated + API), **"an external application can do this"** (no assumed API), and **"human action is required"** (manual). **No fake universal automation layer.**

**Preserved:** the frozen EPIC-012A/012B provider estate (provider UI, intelligence, routing), EPIC-012C AI World discovery (source port, relevance/recommendation engines, bell/page), the existing factories, LoopEngine, requirements engine, and every security boundary — **nothing rebuilt, no duplicate provider configuration, no duplicate routing, no second discovery layer**.

## 3. What was implemented

### 3.1 New workspace `@vedmoulya/capability-marketplace` (types → contracts → domain → infrastructure → application)

**Capability graph (`CapabilityGraph` + `capability-types.ts`)** — 20+ normalized capability ids (TEXT_GENERATION, REASONING, CODING, RESEARCH, RAG, VISION, IMAGE_GENERATION, VIDEO_GENERATION, VIDEO_EDITING, AUDIO_GENERATION, TEXT_TO_SPEECH, SPEECH_TO_TEXT, MUSIC, AVATAR, TRANSLATION, DOCUMENT_PROCESSING, EMBEDDINGS, WEB_RESEARCH, BROWSER_AUTOMATION, CODE_EXECUTION, DEPLOYMENT) with an outcome→capability **knowledge catalog** (deterministic decomposition templates, e.g. "Create a 60-second educational video" → Research → Script → Fact verification → Storyboard → Visual generation → Voice generation → Music/audio → Video assembly → Quality evaluation → Final export). **A capability is not assumed to be API-executable** — executability is a per-candidate fact, never implied.

**`CapabilityDecomposer`** — outcome → ordered execution steps (id, title, capability, purpose) + the set of required capabilities. Deterministic templates for known outcome patterns (video, article, image, audio, web research, code, data analysis, etc.) with an honest general fallback that never pretends to know a specialized pipeline.

**Integration types (`IntegrationClassifier`)** — every candidate declares NATIVE_API / DIRECT_PROVIDER / OPEN_SOURCE / LOCAL_MODEL / GITHUB_PROJECT / EXTERNAL_APPLICATION / MANUAL_STEP / UNKNOWN, derived from the candidate's own facts (a configured provider model with an API → automatable; a tool only available inside an external application → EXTERNAL_APPLICATION with **no assumed API**; a GitHub project → OPEN_SOURCE / SELF_HOSTABLE; a local open-weight model → LOCAL_MODEL). `apiAvailable: 'yes' | 'no' | 'unknown'` is decided from evidence, never assumed.

**Candidate classification (`CapabilityCandidate`)** — READY (configured API model) / CONFIGURE (discovered provider with strong evidence / unconfigured registry provider) / EVALUATE (GitHub project requiring testing) / EXTERNAL (external app only) / MANUAL (human editing required) / UNAVAILABLE / UNKNOWN — each with reasons.

**`AutomationBoundaryEngine`** — per step: FULLY_AUTOMATED / PARTIALLY_AUTOMATED / HUMAN_APPROVAL / MANUAL. Never claims full automation where the provider/API does not support it (open-source candidates are at most PARTIALLY_AUTOMATED until setup+verification; external applications stay PARTIALLY_AUTOMATED/MANUAL until a confirmed API; irreversible steps gate automation behind HUMAN_APPROVAL). Plan-level `overall()` + automation percent.

**`QualityFirstSelector`** — selection priority **CAPABILITY → QUALITY → PRECISION → ACCURACY → EVIDENCE → RELIABILITY → AVAILABILITY → USER PREFERENCE → FREE/LOCAL → COST → LATENCY**. The cheapest tool never wins when it produces inferior output; quality-first ties break toward free/local, then cost — never the reverse.

**`ApprovalEngine`** — irreversible actions (publish / send / deploy / purchase / delete / externally share) detected from step title+purpose; irreversible steps become explicit **human approval points** in the plan.

**`CapabilityPlanner`** — the orchestrator: OUTCOME → DECOMPOSE → MATCH (configured providers + local models + AI World discoveries through the narrow `CapabilitySourcePort`) → CLASSIFY → QUALITY-FIRST SELECT → ASSEMBLE the `FactoryCapabilityPlan` (requestedOutcome, requiredCapabilities, candidateProviders, executionSteps, automationLevel+percent, estimatedCost/estimatedTime **only when evidence exists**, evidence[], risks[], humanApprovalPoints[], unavailableCapabilities[], recommendations[]). Missing capabilities are reported honestly — never filled with a fake tool.

**Recommendations (`buildRecommendations`)** — the configuration bridge: CONFIGURE_PROVIDER (deep-link into the existing provider configuration, suggested family) / EVALUATE_LOCAL_MODEL / REVIEW_EXTERNAL_TOOL — **no duplicated configuration screens**.

**`CapabilityMarketplaceApplicationService`** — the `capability.*` contract: `plan` (deterministic core + optional non-fatal AI enrichment seam over the frozen runtime), `getPlan` / `listPlans` (owner-scoped, IDOR refused), `capabilities` (marketplace view model: which capabilities are READY / CONFIGURE-able with best candidate). **Bounded `CapabilityPlanStore`** (FIFO 50/owner) — never an unbounded sink.

### 3.2 Gateway (`services/api`)

- `capabilityMarketplace.*` namespace: `plan` (heavy tier — builds the full plan) / `getPlan` / `listPlans` / `capabilities` (standard tier) — auth + rate limits + the standard **IDOR guard** (foreign plan ids resolve to null/empty, never leak).
- `CapabilitySourcePorts.ts` — the gateway adapter that feeds **existing** provider intelligence (`listByCapability`), **existing** local-model discovery, and **existing** AI World discoveries into the narrow planner port (request-context owner scoping; zero duplication of provider/AI-World logic).
- `CapabilityEnrichmentPort.ts` — **LIVE AI enrichment over the frozen runtime adapter**: a single economy `classification` call via `AIOrchestratorSpecialistPort` (the same port the loop + factory reuse) runs inside every `plan()`; the result (natural-language summary + AI-suggested steps/capabilities, provider/model provenance) attaches as an **advisory `aiInsight` overlay ONLY when the provider returns `confident: true`**. The outcome text is delimited as **untrusted data** in the prompt (injection-hardened), capabilities are whitelisted against the graph, the summary is length-capped at parse time, and a failure or timeout NEVER fails the deterministic plan (swallowed; no insight attached).

### 3.3 Web experience (`apps/web`)

- **Dedicated `/capability-marketplace` page** (nav: "Capability Market"): plan builder (outcome input → CREATE PLAN), the premium plan view — capability checklist (✓ Research ✓ Script ✓ Fact Check ✓ Voice ✓ Visuals ✓ Assembly ✓ Quality Check), per-step AI plan table (step → chosen tool → integration type), **Automation `████████░░ 80%`** bar, **Requires approval** list (e.g. Final publish), evidence + risks + recommendations (Configure provider / Evaluate local model / Review external tool deep links), unavailable capabilities called out honestly, and plan history.
- **`/applications` third mode — "Capability Plan"**: shared `CapabilityPlanBuilder` component lets a factory request start from a capability plan ("Create a complete automated video" → plan → then hand off to the existing factory flow) alongside the existing Product Intelligence and Direct Factory modes.
- api-client hooks: `useCapabilityPlan` / `useCapabilityGetPlan` / `useCapabilityListPlans` / `useCapabilityMarketplaceView`.

## 4. Security

- **Discovered tools/repositories are untrusted input** — the planner consumes AI World evidence as-is (flagged by the EPIC-012C SecurityScanner) and never auto-installs, auto-clones or auto-executes anything; GitHub resources are EVALUATE-only with explicit user action.
- **Never pretend an external application has an API** — `apiAvailable` is evidence-derived; EXTERNAL_APPLICATION candidates carry an explicit note and REVIEW_EXTERNAL_TOOL recommendation instead of automation claims.
- **Irreversible actions require approval** — publish / send / deploy / purchase / delete / share are never silently automated.
- **No credentials exposed, no private data sent to unapproved providers** — candidates are matched locally from existing intelligence; enrichment is opt-in, non-fatal and flows through the frozen runtime adapter.
- **Owner isolation structural** — plan state keys on the caller's own userId; the gateway IDOR guard refuses foreign access (test-verified).

## 6. Honest limitations

- **AI enrichment of plans is now LIVE** — when a provider is configured, every `plan()` makes one bounded economy AI call for the advisory `aiInsight` overlay (summary + AI-suggested steps/capabilities). The **deterministic capability planner remains authoritative** — the overlay is advisory-only, only attaches when the provider is confident, and a provider failure/timeout never affects the plan (non-fatal, tested). Without a configured provider, plans are created exactly as before (no insight). Live provider execution is still an operator step (same machine constraint as all prior epics).
- **Estimated cost/time are only reported when evidence exists** (a candidate with API/pricing facts) — otherwise the plan says UNKNOWN; never fabricated.
- The plan store is process-local in-memory (same persistence horizon as the other hermetic defaults; injectable via the port).
- No Postgres/Docker on this machine (unchanged from EPIC-011/012/012A/012B/012C).
