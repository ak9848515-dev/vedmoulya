## 11. Architectural Risks

### Risk 1: Performance — Multiple Store Queries

**Concern:** Qualification now queries delivery + commercial stores, potentially N+1 per opportunity.

**Mitigation:**

- Bounded retrieval: `store.list({ userId, category: 'DELIVERY_OUTCOME', limit: 50 })` (single query, then filter in memory)
- Passive decay only at read time (no writes during qualification)
- Existing qualification is already O(1) per opportunity — this adds 1-2 async queries

**Assessment:** **LOW RISK** — bounded queries, no unbounded scans.

### Risk 2: Evidence Linking — Canonical References

**Concern:** How do we know delivery/commercial outcomes relate to THIS opportunity?

**Current reality:**

- `DeliveryOutcomeMemoryRecord` has optional `opportunityId?`
- `CommercialLearningSignal` has optional `opportunityId?`
- Not all historical outcomes carry `opportunityId` (legacy data, or opportunity wasn't linked)

**Mitigation:**

- Filter by `opportunityId` when present
- If no opportunity-linked history, report `INSUFFICIENT_EVIDENCE` (honest — not a fallback to "all user history")
- **Do NOT** guess relationship by title/client similarity

**Assessment:** **MEDIUM RISK** — requires careful filtering logic; legacy data may lack `opportunityId`.

### Risk 3: Cross-User Leakage

**Concern:** Reading delivery/commercial history must be owner-scoped.

**Mitigation:**

- All queries pass `userId: record.ownerId` (from authenticated session, not client input)
- Store methods enforce owner scoping (`getByFingerprint` includes userId in fingerprint; `list({ userId })` filters)
- Existing IDOR tests verify this

**Assessment:** **LOW RISK** — existing store contracts enforce isolation.

### Risk 4: Confidence Inflation

**Concern:** Small samples claiming high confidence.

**Mitigation:**

- Reuse `computeConfidence` — already has conservative rules (sampleCount >= 5 for HIGH)
- Test: "small sample produces conservative confidence"

**Assessment:** **LOW RISK** — existing confidence engine handles this.

### Risk 5: Unknown vs False Conflation

**Concern:** No delivery history might be interpreted as "0% delivery success" instead of "UNKNOWN".

**Mitigation:**

- Empty history → `level: 'INSUFFICIENT'`, `sampleCount: 0`, `successCount: 0`
- `overallAssessment: 'INSUFFICIENT_EVIDENCE'` when both delivery and commercial are insufficient
- Test: "no delivery history → deliveryEvidence.level = 'INSUFFICIENT'"

**Assessment:** **LOW RISK** — explicit INSUFFICIENT level distinguishes from LOW.

### Risk 6: API Breaking Change

**Concern:** Existing consumers of `qualifyOpportunity` might break if response shape changes.

**Mitigation:**

- `valueIntelligence` is **optional** field — existing consumers ignore it
- No existing fields removed or renamed
- Additive change only

**Assessment:** **LOW RISK** — backwards compatible.

## 12. Cross-User Learning Support

**Current status:** **NOT SUPPORTED — must remain isolated.**

**Evidence:**

**S6.3 requirement:** All delivery/commercial evidence queries MUST pass `userId: record.ownerId`.

**No aggregate cross-user learning exists** — and S6.3 must not introduce it.

### Risk 7: Commercial Status Semantic Drift
**Concern:** Confusing `PAID` with "commercial success" or treating pending as failure.

**Mitigation:**
- Only `PAID` increments `paidCount`
- Pending/manual review/invoice pending increment `pendingCount` (activity, not success)
- Cancelled increments `cancelledCount` (explicit non-success)
- Test: "pending invoice does NOT count as paid"

**Assessment:** **LOW RISK** — explicit status counting prevents drift.

**Note:** Some tests overlap with existing S5.1 qualification tests — extend those rather than duplicating.
