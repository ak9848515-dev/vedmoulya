## Preamble

This document establishes the **Compliance & Governance Framework** for VedMoulya. It defines the regulatory landscape in which the platform operates, the compliance principles that govern all architectural decisions, and the policies that ensure user data is protected, rights are respected, and obligations are met.

This document is the authoritative reference for all compliance-related decisions across the VedMoulya platform. Every mission — Architecture, Engineering, Product — must align with the requirements defined here.

## Compliance Policies

### Policy 1: Consent Management

**Objective:** Ensure user consent is obtained, recorded, honored, and revocable for all personal data processing.

**Reference:** ENG-003/D08 (Information Governance — Policy 2: Privacy and Consent)

**Requirements:**

1. **Explicit Consent** — Consent is actively given (pre-checked boxes are not consent)
2. **Informed Consent** — User understands what data is collected, why, and for how long
3. **Granular Consent** — User can consent to specific processing purposes independently
4. **Revocable Consent** — User can withdraw consent at any time, as easily as it was given
5. **Time-Bound Consent** — Consent expires after a defined period and must be renewed
6. **Auditable Consent** — Every consent action (given, modified, withdrawn) is recorded
7. **Consent Records** — Proof of consent is maintained for the duration of processing + regulatory period

**Consent Categories (from ENG-003/D08):**

| Category                | Consent Required | Legal Basis                                    |
| ----------------------- | ---------------- | ---------------------------------------------- |
| Platform Operation      | No               | Contractual necessity (performance of service) |
| Personalization         | Yes              | Legitimate interest (with opt-out)             |
| AI Processing           | Yes              | Consent                                        |
| Data Sharing (internal) | Yes              | Consent                                        |
| Data Sharing (external) | Yes              | Consent                                        |
| Analytics (personal)    | Yes              | Consent (opt-in)                               |
| Analytics (anonymized)  | No               | Legitimate interest                            |
| Marketing               | Yes              | Consent (opt-in)                               |

**Implementation Requirements:**

- Consent management is automated and enforced at the architectural level (ENG-002 service contracts, ENG-003 information lifecycle)
- Consent records are maintained in the Audit Service (ENG-002)
- Consent withdrawal triggers automatic cessation of processing and offers data deletion

### Policy 2: Data Subject Rights

**Objective:** Enable users to exercise their privacy rights under applicable regulations.

**Rights Implementation:**

| Right                                  | Regulation         | VedMoulya Implementation                                           | SLA                            |
| -------------------------------------- | ------------------ | ------------------------------------------------------------------ | ------------------------------ |
| **Right to Access**                    | GDPR Art. 15, CCPA | User can view all personal data through profile/download           | 30 days (GDPR), 45 days (CCPA) |
| **Right to Rectification**             | GDPR Art. 16, CCPA | User can correct personal data through profile                     | 30 days                        |
| **Right to Erasure (Right to Delete)** | GDPR Art. 17, CCPA | User can request deletion; automated deletion per retention policy | 30 days                        |
| **Right to Portability**               | GDPR Art. 20       | User can export personal data in machine-readable format           | 30 days                        |
| **Right to Restrict Processing**       | GDPR Art. 18       | User can limit processing of their data                            | Immediate                      |
| **Right to Object**                    | GDPR Art. 21       | User can object to specific processing (e.g., AI processing)       | Immediate                      |
| **Right to Opt-Out (Sale/Share)**      | CCPA               | User can opt out of data sale or sharing                           | Immediate                      |
| **Right to Non-Discrimination**        | CCPA               | No service denial or price change for exercising rights            | Continuous                     |

**Request Handling Process:**

```text
User submits request (via profile / email / API)
  ↓
Identity Service verifies user identity
  ↓
Request routed to appropriate service (based on request type)
  ↓
Service processes request (access, correct, delete, export)
  ↓
Audit Service records the request and outcome
  ↓
User notified of completion
  ↓
If deletion: verify data is unrecoverable; provide confirmation
```

### Policy 3: Data Retention and Deletion

**Objective:** Retain personal data only as long as necessary and securely delete it thereafter.

**Reference:** ENG-003/D03 (Information Lifecycle — Stages 9 and 10)

**Retention Schedule:**

| Information Type     | Active Retention     | Archived Retention    | Total                | Regulatory Basis                 |
| -------------------- | -------------------- | --------------------- | -------------------- | -------------------------------- |
| Identity             | Account lifetime     | 3 years post-deletion | Account + 3 years    | GDPR Art. 5(1)(e), tax/legal     |
| Knowledge (personal) | Account lifetime     | 3 years post-deletion | Account + 3 years    | User management                  |
| Goal                 | Completion + 1 year  | 3 years               | Completion + 4 years | User management                  |
| Skill                | Account lifetime     | 3 years post-deletion | Account + 3 years    | User management                  |
| Progress             | Account lifetime     | 3 years post-deletion | Account + 3 years    | Service improvement              |
| Memory               | 90 days (active)     | 2 years               | ~2 years             | Service improvement              |
| Decision             | 3 years              | 7 years               | 7 years              | Legal/regulatory                 |
| Plan                 | Superseded + 90 days | 3 years               | Superseded + 3 years | Business purpose                 |
| Execution            | 1 year               | 5 years               | 5 years              | Service improvement              |
| Finance              | Account lifetime     | 7 years post-deletion | Account + 7 years    | Tax/legal (GDPR, financial regs) |
| Career               | Account lifetime     | 3 years post-deletion | Account + 3 years    | User management                  |
| Health               | 1 year               | 3 years               | 3 years              | Consent-based                    |
| Business             | Account lifetime     | 5 years post-deletion | Account + 5 years    | Business/legal                   |
| Marketplace          | Indefinite (active)  | 7 years               | 7+ years             | Legal/tax (transaction records)  |
| Analytics (personal) | 90 days (raw)        | 3 years (aggregated)  | 3 years              | Service improvement              |
| Audit                | 7 years              | 7 years               | 7 years              | SOC 2, regulatory                |
| Configuration        | Active lifetime      | 1 year superseded     | Active + 1 year      | Operational                      |
| Context              | Not retained         | Not retained          | None                 | Purpose limitation               |

**Deletion Requirements:**

1. Hard deletion is permanent and irrecoverable (verified by cryptographic checksum)
2. Soft deletion (recoverable) is available for 30 days post-user-request
3. Cascade deletion respects information dependency rules (ENG-003/D06)
4. Legal holds override deletion — documented and audited
5. Deletion confirmation is provided to the user

### Policy 4: Data Processing and Sharing

**Objective:** Ensure personal data is processed and shared only with appropriate safeguards.

**Processing Principles:**

1. **Purpose Limitation** — Data is processed only for the purpose for which it was collected
2. **Data Minimization** — Only the minimum data necessary is processed
3. **Minimum Context (AI)** — AI providers receive only the minimum context needed for each task (ARC-005/D04)
4. **No Training on User Data** — AI providers are contractually and architecturally prevented from training on user data
5. **Third-Party Processing** — All third-party processors are vetted, contracted, and audited

**Third-Party Processor Requirements:**

| Requirement                     | Description                                      |
| ------------------------------- | ------------------------------------------------ |
| Data Processing Agreement (DPA) | Executed DPA covering GDPR Art. 28 requirements  |
| Security Assessment             | SOC 2 Type II report or equivalent               |
| Sub-processor Notification      | Right to object to sub-processors                |
| Breach Notification             | Contractual obligation to notify within 24 hours |
| Deletion Commitment             | Data deleted upon contract termination           |
| Audit Right                     | Right to audit processor's controls              |

**Current/Planned Data Processors:**

| Processor                                      | Purpose        | Data Categories          | DPA Status          |
| ---------------------------------------------- | -------------- | ------------------------ | ------------------- |
| AI Providers (OpenAI, Google, Anthropic, etc.) | AI inference   | Minimal context (no PII) | Required before use |
| Cloud Infrastructure Provider                  | Infrastructure | All data (encrypted)     | Required before use |
| Email/SMS Provider                             | Notifications  | Contact information      | Required before use |
| Payment Processor (Stripe, etc.)               | Payments       | Payment data (tokenized) | Required before use |

### Policy 5: Data Breach Response

**Objective:** Detect, respond to, and notify affected parties of data breaches in a timely manner.

**Breach Definition:** A breach of security leading to the accidental or unlawful destruction, loss, alteration, unauthorized disclosure of, or access to, personal data transmitted, stored, or otherwise processed.

**Response Process:**

```text
PHASE 1: DETECTION (0-1 hour)
  ├── Automated detection (intrusion detection, anomaly alerts)
  ├── User/customer report
  ├── Third-party notification
  └── Security team on-call notification

PHASE 2: ASSESSMENT (1-4 hours)
  ├── Determine scope (what data, what systems, what users affected)
  ├── Determine severity (PII exposed, credentials exposed, etc.)
  ├── Contain the breach (isolate affected systems, revoke access)
  └── Document findings

PHASE 3: NOTIFICATION (24-72 hours)
  ├── GDPR: Notify supervisory authority within 72 hours
  ├── CCPA: Notify affected residents without unreasonable delay
  ├── Affected users: Notify with details of what happened and what they should do
  └── Law enforcement: Notify where criminal activity suspected

PHASE 4: REMEDIATION (1-30 days)
  ├── Fix root cause
  ├── Recover affected data (if possible)
  ├── Enhance controls to prevent recurrence
  └── Post-mortem and documentation

PHASE 5: REGULATORY FOLLOW-UP (1-90 days)
  ├── Respond to regulatory inquiries
  ├── Implement required corrective actions
  └── Update incident response plan based on lessons learned
```

**Breach Notification Template (to affected users):**

- What happened (in plain language)
- What data was involved
- What we have done in response
- What you should do (password reset, monitor accounts, etc.)
- Who to contact for more information
- Regulatory authority contact information

### Policy 6: Data Protection Impact Assessment (DPIA)

**Objective:** Identify and mitigate privacy risks for high-risk data processing activities.

**When a DPIA is Required:**

1. Systematic and extensive profiling with significant effects on individuals
2. Large-scale processing of special categories of data (health, biometric, genetic)
3. Large-scale, systematic monitoring of public areas
4. Processing of vulnerable persons' data (children, employees)
5. Combining datasets in novel ways
6. Using new technologies for data processing
7. Processing that prevents individuals from exercising a right or using a service

**DPIA Process:**

```text
1. IDENTIFY need for DPIA
2. DESCRIBE processing (nature, scope, context, purpose)
3. ASSESS necessity and proportionality
4. IDENTIFY and assess risks to rights and freedoms
5. IDENTIFY mitigation measures
6. DOCUMENT and obtain approval from DPO/Privacy Officer
7. INTEGRATE mitigation into system design
8. REVIEW and update as processing changes
```

**DPIA Register:** All completed DPIAs are maintained in a register accessible to the DPO and regulatory authorities upon request.

### Policy 7: AI Governance and Ethics

**Objective:** Ensure AI systems are transparent, fair, accountable, and aligned with human values.

**AI Governance Principles:**

| Principle          | Requirement                                          | Implementation                                                                                       |
| ------------------ | ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| **Transparency**   | Users are informed when interacting with AI          | AI-generated content labeled; AI coaching identified as AI                                           |
| **Explainability** | AI decisions and recommendations are explainable     | ARC-002 (Decision Explanation), ARC-005 (Response Validation)                                        |
| **Fairness**       | AI systems do not discriminate or bias against users | Bias testing; diverse training data; regular fairness audits                                         |
| **Accountability** | Human oversight of AI systems                        | Human-in-the-loop for high-risk decisions; escalation path                                           |
| **Safety**         | AI systems are safe and secure                       | ARC-005 (Response Validation — 6 gates: Safety, Policy, Hallucination, Quality, Consistency, Format) |
| **Privacy**        | AI respects user privacy                             | Minimum context principle (ARC-005); no training on user data                                        |
| **Human Autonomy** | Users maintain control over their decisions          | Recommendations are advisory; users make final decisions                                             |

**High-Risk AI Systems (per EU AI Act):**
The following VedMoulya capabilities may be classified as high-risk AI systems:

- Career path recommendations that significantly affect professional opportunities
- Financial guidance that significantly affects financial well-being
- Health and productivity analysis that affects work patterns

**Requirements for High-Risk AI:**

1. Human oversight mechanisms
2. Transparency and explainability documentation
3. Accuracy, robustness, and cybersecurity testing
4. Bias monitoring and mitigation
5. Detailed technical documentation
6. Conformity assessment before deployment

### Policy 9: International Data Transfers

**Objective:** Ensure personal data transferred across borders is adequately protected.

**Transfer Mechanisms:**

| Mechanism                               | When Used                                                                    | Requirements                                         |
| --------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------- |
| **Adequacy Decision**                   | Transfer to country with EU adequacy decision (UK, Japan, South Korea, etc.) | Monitor adequacy status                              |
| **Standard Contractual Clauses (SCCs)** | Transfer to countries without adequacy decision                              | Execute EU-approved SCCs with processor              |
| **Binding Corporate Rules (BCRs)**      | Intra-group transfers                                                        | Approved by EU supervisory authority                 |
| **Transfer Impact Assessment (TIA)**    | Required for SCC transfers                                                   | Assess legal framework of recipient country          |
| **Supplementary Measures**              | Required if TIA indicates insufficient protection                            | Encryption, pseudonymization, contractual guarantees |

**Data Residency Requirements:**

- EU user data: stored in EU (or adequacy-determined country)
- US user data: stored in US (or with appropriate safeguards)
- Future: per-region data residency as required by local law
- Data residency is enforced at the architectural level (information classification and storage policies)

## Compliance Requirements Per Mission

### ARC-001 (System Architecture)

- Principle #6 (Privacy First) — **Requirement:** All systems must implement privacy by design
- Principle #11 (Secure by Design) — **Requirement:** All systems must implement security controls
- **Compliance Contribution:** Foundational architecture principles that all other missions follow

### ARC-002 (Decision Intelligence)

- **Requirement:** All decisions must be explainable (GDPR Art. 22 — automated decision-making)
- **Requirement:** Users must be able to contest automated decisions
- **Requirement:** AI-generated decisions must be labeled as such (EU AI Act)
- **Compliance Contribution:** Decision explainability, confidence scoring, feedback loops

### ARC-003 (Knowledge Graph)

- **Requirement:** Knowledge provenance must be traceable (regulatory audit)
- **Requirement:** Personal knowledge must be deletable upon user request
- **Requirement:** Knowledge quality must be measurable (accuracy for regulated domains)
- **Compliance Contribution:** Entity-relationship model, provenance tracking, quality scoring

### ARC-004 (Execution Intelligence)

- **Requirement:** Execution policies must enforce compliance rules (hard policies for privacy/safety)
- **Requirement:** Execution history must be auditable
- **Requirement:** User capacity must be respected (no burnout — ethical obligation)
- **Compliance Contribution:** Policy enforcement, execution audit, human-centric execution

### ARC-005 (AI Orchestrator)

- **Requirement:** Minimum context principle — only necessary data sent to AI providers (GDPR data minimization)
- **Requirement:** AI providers must not train on user data (contractual + architectural)
- **Requirement:** AI responses must be validated for safety, policy, and quality (EU AI Act)
- **Compliance Contribution:** Context assembly, provider contracts, response validation

### ENG-001 (Domain Model)

- **Requirement:** User must be the central entity with ownership of personal data
- **Requirement:** Domain events must capture compliance-relevant occurrences
- **Requirement:** Bounded contexts must respect data access boundaries
- **Compliance Contribution:** Domain entities for user rights, domain events for compliance

### ENG-002 (Service Contracts)

- **Requirement:** Security Service must enforce authentication and authorization
- **Requirement:** Audit Service must maintain immutable compliance trail
- **Requirement:** Service contracts must enforce classification-based access control
- **Requirement:** Consent must be checked before personal data processing
- **Compliance Contribution:** Security, audit, identity, consent enforcement

### ENG-003 (Information Architecture)

- **Requirement:** Information must be classified (PERSONAL, SENSITIVE, REGULATED)
- **Requirement:** Information lifecycle must enforce retention and deletion
- **Requirement:** Users must own their personal information
- **Requirement:** Information flow must be traceable (lineage)
- **Compliance Contribution:** Classification, lifecycle, ownership, flow governance

### ENG-004 (Solution Blueprint)

- **Requirement:** Deployment must comply with data residency requirements
- **Requirement:** Offline mode must respect consent and deletion
- **Requirement:** Extensibility model must include compliance review
- **Compliance Contribution:** Deployment compliance, extensibility governance
